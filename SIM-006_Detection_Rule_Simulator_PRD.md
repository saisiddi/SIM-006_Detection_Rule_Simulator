## 1. Purpose & Problem Statement

**Purpose:** Simulate detection rules and validate whether telemetry, identity, firmware, safety, or cyber events trigger warnings or hard-fail gates.

**Problem it solves:** Detection rules must be validated against diverse event inputs. Without this simulator, testing detection logic requires coordinating multiple other simulators simultaneously — this tool lets the rule engine be built, tested, and validated in isolation using synthetic/pre-generated events, before wiring into real telemetry or production systems.

**Business goal:** Enable the detection rule engine to be developed, tested, and validated against simulated events before integrating with real telemetry or production systems.

## 5. Data Models (Pydantic v2)

### 5.1 `Event` model
```python
class Event(BaseModel):
    event_type: Literal["telemetry", "identity", "firmware", "cyber"]
```

```python
class EvaluationRequest(BaseModel):
```

```python
class RuleEvaluationResult(BaseModel):
```

## 6. Functional Requirements — The 8 Rules (Exact Logic)

Implement each as an independent, pure function: `(event: Event) -> RuleEvaluationResult`.

| Rule ID | Name | Trigger Condition | Result on Trigger |
|---|---|---|---|
| **R-01** | Replay attack detected | Timestamp is stale (older than an acceptable window) OR sequence_number duplicates a previously seen value | HARD_FAIL |
| **R-02** | Missing telemetry timestamp | `timestamp` field is `null` on a telemetry event | HARD_FAIL |
| **R-03** | Invalid or expired certificate | `certificate_expiry` is in the past, or certificate is malformed/missing on an identity event | HARD_FAIL |
| **R-04** | Firmware hash mismatch | `firmware_hash != expected_firmware_hash`, or firmware version is unrecognized | HARD_FAIL |
| **R-05** | Voltage out of safe range | `voltage_v < 40` or `voltage_v > 56` (48V pack) | WARN (escalate to HARD_FAIL if far outside range — define your own secondary threshold, e.g. beyond ±10% of the limit) |
| **R-06** | Critical temperature | `temperature_c > 55` or `temperature_c < -20` | WARN or HARD_FAIL depending on severity (mirror R-05's escalation pattern) |
| **R-07** | Open cyber incident linked to battery | `open_incident == True` | HARD_FAIL |
| **R-08** | Physically impossible telemetry | `soc_percent` increases by more than a defined threshold (e.g. >5%) between readings while `charging_source_present == False` | HARD_FAIL |

**Gate aggregation rule:** `overall_gate` = the **worst result** across all evaluated rules, where `HARD_FAIL > WARN > PASS`. If any rule is HARD_FAIL, the overall gate is HARD_FAIL regardless of how many rules passed.

**Rule evaluation modes:**
- Evaluate a specific subset: `rule_ids: ["R-01", "R-02", "R-05"]`
- Evaluate all 8: `rule_ids: "all"`
- Support rule override/bypass scenarios (a rule can be explicitly excluded from evaluation and will not count toward the gate decision — this should be logged, not silent)

## 9. Architecture

```
Event (JSON)
     │
     ▼
 RuleEngine.evaluate(event, rule_ids)
     │
     ├── iterates over each selected rule
     ├── runs rule_fn(event) → RuleEvaluationResult
     │
     ▼
 List[RuleEvaluationResult]
     │
     ▼
 Gate Aggregator → overall_gate = worst(result across all rules)
     │
     ▼
 EvaluationResponse (JSON, simulated=true)
```

**Design principle:** `RuleEngine` should be a thin orchestrator. Each rule (R-01 … R-08) is its own function/class registered in a rule registry (e.g. a dict mapping rule_id → callable), so adding a 9th rule later never requires touching the engine itself.
